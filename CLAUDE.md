Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Use `bun test` instead of `jest` or `vitest`
- Use `bun build <file.html|file.ts|file.css>` instead of `webpack` or `esbuild`
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`
- Use `bun run <script>` instead of `npm run <script>` or `yarn run <script>` or `pnpm run <script>`
- Use `bunx <package> <command>` instead of `npx <package> <command>`
- Bun automatically loads .env, so don't use dotenv.

## APIs

- `Bun.serve()` supports WebSockets, HTTPS, and routes. Don't use `express`.
- `bun:sqlite` for SQLite. Don't use `better-sqlite3`.
- `Bun.redis` for Redis. Don't use `ioredis`.
- `Bun.sql` for Postgres. Don't use `pg` or `postgres.js`.
- `WebSocket` is built-in. Don't use `ws`.
- Prefer `Bun.file` over `node:fs`'s readFile/writeFile
- Bun.$`ls` instead of execa.

## Debugging
When debugging issues, exhaust the most likely root cause hypothesis thoroughly before moving to the next. Avoid shotgun debugging — form a clear hypothesis, test it, and only move on when it's definitively ruled out. Especially for Slack bot issues, check app configuration and permissions before assuming code bugs.

## Frontend

Muninn's web UI (chat + dashboard) is **server-rendered** via `Bun.serve()` + Hono — not React/vite. If a client bundle is ever needed, use Bun HTML imports (`Bun.serve({ routes: { "/": index } })`), never webpack/vite.

For more information, read the Bun API docs in `node_modules/bun-types/docs/**.mdx`.

## Muninn Project

Personal AI assistant — multi-bot Telegram platform with pluggable AI connectors (Claude CLI, Copilot SDK, OpenAI-compat, or Claude SDK), a live Hono dashboard, semantic memory, goal tracking, scheduled tasks, proactive watchers, and voice support.

### Running

```bash
bun run db:up               # Start Postgres (requires Docker)
bun run db:migrate:baseline # Mark existing migrations as applied (first time only)
bun run db:migrate          # Apply pending migrations
bun run dev                 # Dev with --watch
bun run start               # Production
bun run dev:chat            # Chat-only (no scheduler, port 3011)
```

### Multi-Bot Architecture

One muninn process runs every bot: each gets its own Grammy Telegram bot and AI connector, and they share the DB, dashboard and scheduler.

Each bot lives in `bots/<name>/` with its own:
- `CLAUDE.md` — persona (auto-loaded by Claude CLI as project instructions)
- `config.json` — per-bot overrides (connector, model, thinking tokens, timeout, baseUrl)
- `.mcp.json` — MCP tools (Gmail, Calendar, etc.)
- `.claude/settings.json` — tool permissions

Each bot selects its AI connector via `config.json` (`"connector"`: `"claude-cli"`, `"copilot-sdk"`, `"openai-compat"`, or `"claude-sdk"`). Claude CLI is spawned with `cwd: bots/<name>/` so it auto-discovers all config and stores conversation history separately. See "Switching chat connector" below for what each connector does and when to pick it; the Conventions section covers their internal mechanics.

A bot is active if its folder has a `CLAUDE.md` and a matching `TELEGRAM_BOT_TOKEN_<NAME>` env var.

### Database

PostgreSQL + pgvector via Docker (single container).

- URL: `postgresql://muninn:muninn@127.0.0.1:5435/muninn`
- Schema: `db/init.sql` (full consolidated schema, applied by Docker on first start). Anywhere Docker does *not* apply it — a nais pod, whose Cloud SQL instance is private-IP with app credentials only inside the pod — **`bun db/provision.ts --yes`** (`db:provision`) is the runnable form: it applies `init.sql` and baselines in one command, from the image, with no psql and no file transport. **`--yes` is required and the resolved host/database is printed before it is asked for** — Bun auto-loads `.env`, so a bare invocation in a checkout would resolve whatever that file names, and this command writes a schema; an unrecognised flag is refused rather than ignored, so a typo'd `--dryrun` cannot become a real run. **The predicate is the WHOLE table set, parsed out of `init.sql` itself — and it lives in ONE module, `db/schema-state.ts`, shared with `db/require-provisioned.ts`** (which is what the container entrypoint runs and what PRINTS the remedies; it kept its own weaker copy for one round, and that copy was the fatal path) — not `users`, which is init.sql's FIRST table while `schema_migrations` is its LAST: a `psql -f db/init.sql` that died mid-file therefore has `users` and no ledger in almost every case, which a `users`-only predicate reads as "provisioned but never baselined", whose remedy (`--baseline`) SUCCEEDS, satisfies `require-provisioned.ts`, boots the pod on a stump of a schema and records every shipped migration so nothing can repair it. FIVE states, one of which writes: complete (refused; told to baseline only when the ledger is genuinely empty), **incomplete** (refused by name, listing present and missing, told explicitly NOT to baseline), **lone-ledger** (only `schema_migrations`, with or without rows — what `db:migrate` or `db:migrate:baseline` against an empty database leaves; the remedy is `DROP TABLE schema_migrations`, never a schema drop), **foreign** (tables, none of them ours — no mid-file diagnosis and no `DROP SCHEMA`, since nothing there was ever init.sql), and empty. The remedy FORKS with the state; that is the point of the enumeration. A role that may not run what `init.sql` asks for is refused separately (`42501`, answered with the Postgres message verbatim plus both causes — the extension, and `permission denied for schema public` on PG15+). **Two separate all-or-nothing steps, not one:** `sql.unsafe` on a whole file is ONE implicit transaction (postgres.js picks the simple protocol when there are no parameters), and `runMigrations`'s baseline inserts are wrapped in their own — the latter added because a PARTIAL baseline passes `require-provisioned.ts`'s `recorded === 0` predicate and then crash-loops the pod inside migration 006. `CREATE EXTENSION vector` still needs an elevated role first on a managed instance — `init.sql`'s `IF NOT EXISTS` short-circuits before the privilege check once it exists
- Migrations: `db/migrations/` (numbered `.sql` and `.ts` files, tracked in `schema_migrations` table)
- Tables: `users` (canonical user identity), `messages`, `activity_log`, `memories` (with vector embeddings + scope), `goals`, `scheduled_tasks`, `watchers` (incl. `last_success_at` — "the checker last covered its window up to here", NOT moved by quiet-hours skips or failures the way `last_run_at` is; the email checker bounds its Gmail query on it, see `src/watchers/CLAUDE.md`), `connectors` (named AI connector configurations), `threads` (per-user+bot conversation isolation, optional FK to connectors), `user_settings`, `haiku_usage`, `traces` (spans with parent-child hierarchy + JSONB attributes), `research_citations` + `search_signals` (durable retrieval signals — citations per research answer; hourly harvest of huginn quality attrs before trace cleanup), `message_feedback` (per-assistant-message 👍/👎 from Telegram reactions + web chat), `interest_profiles` (per user+bot Haiku-distilled interests, injected into watcher gate prompts), `user_identities` (the `entra` link: `(provider, tenant, oid) → users.id` + `nav_ident`/`display_name` refreshed on every login — migration 073; the key is `oid` because a NAVident is re-issued, and provisioning is `users` + this row in ONE transaction, never a default thread), `role_overrides` (DB-backed hot overrides for `SUMMARIZER_BOT`/`RESEARCH_BOT`/`HAIKU_BACKEND`, edited from `/models`; beat env at resolution time), `x_link_amplifiers` (cross-run X pointer votes per destination URL; shipped flag-gated OFF — see `captureAmplifyMin` in `src/watchers/CLAUDE.md`)

### Switching Haiku backend (Copilot vs Anthropic vs Vertex vs CLI)

The Haiku router (`src/ai/haiku-direct.ts`) powers the `research_knowledge` decomposer and the three async extractors (memory / goals / schedule). **The decomposer is the one that cannot be switched off**: every `research_knowledge` call decomposes through a Haiku-tier call FIRST, with the user's question in the prompt, so an instance that moves its chat turn to a particular endpoint and leaves the router alone is sending the lookup somewhere else than the answer. The three extractors can be force-disabled (`extractionsForcedOff` on an `entra` identity); the decomposer is how the knowledge tool works. Default behaviour: a bot's `connector` decides — `copilot-sdk` → Copilot SDK, anything else → Claude CLI. Override per-bot in `bots/<name>/config.json` via `haikuBackend`, or process-wide via the `HAIKU_BACKEND` env (debug knob). Watchers (email/x/anthropic) still use `spawnHaiku` directly, which unconditionally spawns the CLI. Only the email watcher truly requires it (Gmail MCP via bot-cwd `.mcp.json` discovery, which the one-shot helpers don't expose); the x/anthropic gate/digest calls run no MCP tools and stay on the CLI only because they share the executor — accepted, since nothing waits on their latency.

| Goal | What to set | Auth |
|---|---|---|
| Bot uses Copilot for both chat + Haiku (e.g. melosys) | `bots/<name>/config.json` → `"connector": "copilot-sdk"` | `gh auth login` (Capra/NAV Copilot subscription) |
| Just one CLI bot on Anthropic SDK for Haiku (e.g. jarvis on faster decomposer, others unchanged) | `bots/jarvis/config.json` → `"haikuBackend": "anthropic"` | `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) |
| All CLI bots on Anthropic SDK for Haiku | `HAIKU_BACKEND=anthropic` in `.env` (affects every bot in this process) | same as above |
| Decomposer + extractors on the same **Vertex AI** endpoint as an `openai-compat` chat turn | `bots/<name>/config.json` → `"haikuBackend": "vertex"` (or `HAIKU_BACKEND=vertex` for every bot), plus `VERTEX_PROJECT_ID` + `VERTEX_REGION`; optional `HAIKU_VERTEX_MODEL` | **Application Default Credentials** — `gcloud auth application-default login` locally, the workload-identity metadata server in a pod. No `OPENAI_API_KEY`. |
| Bot stays fully on Claude CLI (no SDK) | leave `connector` unset or `"claude-cli"`, leave `haikuBackend` unset | none (uses existing CLI auth) |
| Force one backend everywhere (testing / debugging) | `HAIKU_BACKEND=cli` / `anthropic` / `copilot` / `vertex` — trumps per-bot config | auth for chosen backend |
| Reset to defaults | unset `HAIKU_BACKEND` *and* `HAIKU_DIRECT_ENABLED`, drop `haikuBackend` from config.json | n/a |

Diagnostics:
- `bun scripts/smoke-vertex.ts --probe=haiku` drives the SHIPPED router and the SHIPPED decomposer with the Vertex backend selected and reports which backend actually RAN — the router falls back to the Claude CLI on any failure, and on a developer machine that fallback answers perfectly well, so "it answered" is not evidence and `backend=vertex` is.
- The dashboard `haiku_usage` table shows the actual model each call used — `claude-haiku-4.5` (Copilot) vs `claude-haiku-4-5-20251001` (Anthropic / CLI) vs `google/gemini-2.5-flash-lite` (Vertex). If a bot's `knowledge_decompose` span shows the wrong model, the resolution order is doing something unexpected.
- On any backend error the router falls back to CLI and logs `haiku-router <backend> failed, falling back to CLI` — check muninn logs if a bot regresses to CLI speeds. ⚠️ On `MUNINN_PROFILE=nais` there is no CLI to fall back to: that warn line is still emitted, and then the spawn itself throws `HaikuCliUnavailableError` naming the backend and the credential that failed.
- `bun scripts/smoke-haiku-copilot.ts` re-runs the Copilot path end-to-end and prints the model id Copilot actually used.

### Switching chat connector (CLI vs Copilot vs Claude SDK vs OpenAI-compat)

The chat connector handles the main bot turn — assembling the prompt, running tools, streaming the response. Separate from the Haiku router above (which only powers short async extraction calls). Set per-bot in `bots/<name>/config.json` via `connector`.

| Goal | What to set | Auth |
|---|---|---|
| Default — spawns the `claude` CLI per turn (~5–7s cold-start, full MCP surface) | leave `connector` unset, or `"connector": "claude-cli"` | existing CLI login |
| Bot on Capra/NAV Copilot subscription (e.g. melosys) | `"connector": "copilot-sdk"` | `gh auth login` |
| Direct Anthropic transport — no CLI subprocess, no Copilot subscription. Personal bots that want smoother streaming and like-for-like benchmarks vs Copilot. | `"connector": "claude-sdk"` | `ANTHROPIC_API_KEY` (production) or `CLAUDE_CODE_OAUTH_TOKEN` (personal Max via `claude setup-token`) |
| Local model via Ollama / LM Studio / vLLM | `"connector": "openai-compat"` + `"baseUrl": "http://localhost:11434/v1"` | none |
| Gemini on GCP **Vertex AI**, pinned to a region (a deployment that must keep inference inside a named jurisdiction) | `"connector": "openai-compat"` + `"model": "google/gemini-2.5-flash"` (the `<publisher>/<model>` prefix is required — without it Vertex answers 400) + `"baseUrl": "https://<region>-aiplatform.googleapis.com/v1/projects/<project>/locations/<region>/endpoints/openapi"` | **Application Default Credentials** — `gcloud auth application-default login` locally, the workload-identity metadata server in a pod. No `OPENAI_API_KEY`. |

On a **Vertex** `baseUrl` the connector authenticates per REQUEST, not per turn: a Google access token expires in about an hour and a chat thread outlives that. `src/ai/vertex-access.ts` caches and single-flights the token (metadata server first, `gcloud` ADC second) and the connector retries ONCE on a 401 with a freshly fetched one — a 403 is not retried, since that is an identity that may not call the model rather than a stale credential. The `global` region is refused at that seam too, through every door the OpenAI-compatible URL offers — the region-less host, a `global-` host prefix, and `/locations/global/` in the path (normalized: percent-decoded, lowercased, trailing dots stripped). The region-less host is what binds — it is a live route to the global endpoint — while the `global-` prefix and the path segment are conservative hygiene, since measurement shows `endpoints/openapi` does not validate that segment at all — the same rule `resolveVertexConfig` enforces for the Agent SDK's env names. Details: `src/ai/CLAUDE.md`.

The `claude-sdk` connector uses `@anthropic-ai/claude-agent-sdk` with `bypassPermissions` and `settingSources: []` — muninn's prompt-builder delivers the full system prompt. It honors `thinkingMaxTokens`, `extraDirs` (TikTok frame-reading works here too), and `allowedTools`/`excludedTools`. Permission-surface details, the dead per-bot settings.json finding, and the **claude-sdk → claude-cli rollback procedure** (jarvis flipped; do both connector + OAuth-token steps if the token is blocked): `src/ai/CLAUDE.md`.

The **/models** dashboard page shows the active connector per bot — use it to confirm any flip or rollback landed.

## Testing

Always run `bun run test` after adding or changing a feature to verify nothing is broken. Tests are split into three sub-scripts (unit / db / handlers) to avoid `mock.module()` leakage between files:

```bash
bun run test              # All tests
bun run test:unit         # Unit tests only
bun run test:db           # DB integration tests
bun run test:handlers     # Handler tests (with mocks)
```

DB tests require the local Postgres container (`bun run db:up`) and a test database (`bun run db:setup:test`). **`db/provision.test.ts` needs more than that** — it connects to the `muninn` database as an admin and runs `CREATE DATABASE`/`DROP DATABASE`/`CREATE ROLE` against its own scratch database and a purpose-made non-superuser role (the privilege wall a managed instance puts in front of `CREATE EXTENSION` is not provable as superuser). `db:up` and CI both satisfy that; a hand-built container without a `muninn` database, or a role without `CREATEDB`/`CREATEROLE`, fails there rather than at the documented setup step. Test files are co-located with source files (`*.test.ts`). Shared test infrastructure lives in `src/test/`.

**`mock.module` needs its own process, not just its own file.** It invalidates the target module for the whole `bun test` process graph, so any OTHER file already loaded in that chunk which transitively imports the mocked module fails export resolution — e.g. mocking `db/goals.ts` inside `test:unit`'s first chunk breaks `src/profile/generator.ts` with `SyntaxError: Export named 'refreshInterestProfile' not found`. Spreading the real module into the mock (`{...real, override}`) fixes only the mocking file's OWN imports and does not prevent this. A mock.module test therefore gets its own `&& bun test <file>` link in the chain (see `src/profile/`, `task-executor.test.ts`, `data-routes-bot-scope.test.ts`), and says so in its header — the placement is load-bearing and invisible from the file alone.

### Browser checks

Anything that has to be verified **in a browser** goes through Playwright.

- **A spec in `e2e/`** is the default for acceptance. `bun run test:e2e` (30 specs today: `auth-zones`, `chat`, `chat-card-fences` (seeds its own user/thread/messages/draft into Postgres and pins `JIRA_BOT`, so the three chat CARD render sites are driven with no model call), `agents-refresh`, `chat-session-identity`, `chat-viewer-scope`, `entra-identity` (boots a muninn in `MUNINN_AUTH=entra` plus an in-process `node:http` stub Texas, and reads the provisioned rows back out of Postgres), `inspector`, `jira-card`, `plans-write`, `session-expiry`, `summaries-share`, `summaries-delete` (seeds a `draft` + an `applied` source proposal and, when the test DB has none, a `wiki-gardener` watcher; its fake huginn keeps LISTING the deleted doc so the spec pins the client pulling the row again after the post-reindex refetch), `traces-waterfall`, `ws-scope`, `wiki-*` — `wiki-copy-path` registers TWO temp wikis in one process, the second read-only, because the affordance it checks must be live on both, and `wiki-rail-recents` registers two so a globally-keyed localStorage store cannot pass as a per-wiki one, and `wiki-home` registers two because "a bare `/wiki` opens the wiki last opened" is only provable against a wiki that is NOT the server's default). `playwright.config.ts` owns its own server on **3011** with `reuseExistingServer`, so a dev server already on that port is reused as-is. Don't start a server by hand for the suite; let the config decide.
- **Every spawned muninn gets `e2eEnv()`** (`e2e/e2e-env.ts`), spread after `...process.env` and before the spec's own overrides. It blanks two classes of ambient value: the platform tokens (a second long-poller on the real token knocks the production bot off Telegram, 409 getUpdates) and the **instance-profile flags** — `MUNINN_WIKI_READONLY`, `SYNC_REPOS`, the `MUNINN_AUTH` family. `WIKI_READONLY_ROOTS` is deliberately NOT among them: it is a per-root permission GUARD, not a profile flag, and blanking it while `WIKI_EXTRA` still registers the root leaves that wiki writable and egress-reachable (see `src/test/ambient-env.ts`). The names are the same list `bun test`'s preload clears (`src/test/ambient-env.ts`), because the failure is the same: the mini carries `MUNINN_WIKI_READONLY=1`, so its spawned servers came up read-only and the suite was green on the laptop and red there. **A blank must be an explicit `""` assignment, never a delete** — the child re-reads `.env` itself, and an absent name is exactly what makes Bun fall back to the dotenv line.
- **Ports come from `e2e/ports.ts`, never a literal.** Spec files run in parallel and most boot their own muninn; two files both picked 3042 and the loser's requests were answered by the winner's server (an empty page list, not a bind error). `e2e/ports.test.ts` — a `bun test`, in the `bun run test` chain — fails on a duplicate value and on a bare port literal left in a spec.
- **A fresh database is not enough.** `bun run db:seed:e2e` inserts the one user, two threads and one trace that `chat`/`inspector`/`traces-waterfall` need; without it those specs fail (nothing to select) or, worse, **skip themselves green**. CI runs it; a developer's own DB already has content.
- **`playwright-cli`** (skill: `~/.claude/skills/playwright-cli/`, global `@playwright/cli`) drives a page interactively for exploration — snapshot refs, `console`/`network` readout, headless by default. Promote whatever it proves into an `e2e/` spec; evidence left in a transcript is not a test. Its scratch (`.playwright-cli/`) is gitignored.

Two traps regardless of how the page is driven:
- **`bun --watch` never rebuilds the `/wiki` client bundle.** Restart the dev server before any client-side acceptance run, or the previous build is what gets tested.
- Driving `bun run dev` (port **3010**) by hand runs against the developer's real `.env` — live bots, live wikis. Read-only checks only; anything that writes belongs on the 3011 spec server.

### CI

`.github/workflows/ci.yml` runs four jobs on every push to `main` and every PR: `typecheck`, `test` (`bun run db:setup:test` then the full `bun run test` chain), `e2e` (`db:setup:test` → `db:seed:e2e` → `bun run test:e2e`) — each against a `pgvector/pgvector:pg17` service published on **5435**, the port `src/test/setup-db.ts` hardcodes — and `docker-build`, which needs no database: it builds the image twice (default, then `WITH_MEDIA=false WITH_CLI=false WITH_EMBEDDINGS=true`) and asserts what each one carries — including that only the second has the embedding-model cache, that a bogus build-arg value fails the build, that the bots/ COPY tolerates a context with no bot folder, and — by `docker inspect`, never by re-typing the expression — that the image pins `DASHBOARD_PORT`/`DASHBOARD_HOST` and declares the `/api/live` HEALTHCHECK. It carries a `timeout-minutes` because the claude.ai installer and the Debian mirrors are on its critical path.

A runner has **no `.env` at all**, which is the point: it is the only place the suites are pinned to what the repo says rather than to whichever machine last ran them. Two things follow from that and are deliberate:
- **`workers: 1` on CI, `retries: 0` everywhere.** twenty-one spec files boot a muninn of their own — 24 muninn processes (`plans-write` boots 3, `auth-zones` 2 — `MUNINN_LOCAL_ROLE` is per-process, so admin and `user` cannot share one; `summaries-share`'s and `entra-identity`'s second servers are in-process `node:http` stubs, not processes), plus the config's own shared server on 3011; on a 2-core runner the contention shows up as a click landing before the page's inline script attached its listener — a different spec each run. Serial removes it; a retry would have turned it into a silent pass.
- **Only `bots/jarvis/` is tracked**, so CI has one bot and the inspector's bot-switch case skips itself and says so. Six `jira-card` cases skip too — they are opt-in behind `JIRA_CARD_THREAD`/`_USER`/`_DRAFT`.

## Conventions

- DB access: `postgres` npm package (not Supabase client, not Bun.sql)
- Memory/goal/schedule extraction: fire-and-forget async Claude Haiku calls
- Memory scope: `personal` (per-user) or `shared` (visible to all users of a bot) — Haiku auto-classifies during extraction. **On an authenticating instance (`MUNINN_AUTH` ≠ `off`) the READ side narrows to the reader's own rows at both search call sites** (`sharedMemoryReadsAllowed`, `src/auth/policy.ts`): `shared` rows go verbatim into the system prompt under `Shared team knowledge:` with the scope assigned by a fire-and-forget classifier, which is a feature on one instance and one colleague's content entering another's model context on a shared one
- AI output: standard markdown — per-platform formatters convert at send time (`telegram-format.ts`, `web-format.ts`, `slack-format.ts`)
- Conversation threads: per-user+bot named threads for chat isolation; memories/goals/tasks shared across threads. Commands: `/topic`, `/topics`, `/deltopic`. Pre-migration messages (NULL thread_id) visible only in `main` thread.
- Prompt assembly: persona (from CLAUDE.md) + memories (personal + shared) + goals + scheduled tasks + thread-scoped conversation history. Proactive rows (`messages.source` prefixes `watcher:`/`task:`/`goal:`, the complete set — see exported `PROACTIVE_SOURCE_PREFIXES` in `src/db/messages.ts`) are excluded from history via `getRecentMessages`'s opt-in `excludeProactive` flag and reach the prompt only through the bounded alerts block ("Recent proactive messages sent to user", ~300 chars/alert). The dashboard messages endpoint deliberately passes no flag. Real conversation rows always have `source = NULL`.
- AI connectors: `resolveConnector(botConfig)` returns the appropriate executor (`claude-cli`, `copilot-sdk`, `openai-compat`, or `claude-sdk`). All callers use this instead of importing executors directly. Connectors conform to the `AiConnector` type signature.
- Claude CLI connector: spawned with `cwd: bots/<name>/` — auto-discovers MCP, settings, stores history there. Output: `--output-format stream-json --verbose` (NDJSON events with tool_use blocks); `--verbose` is required with `-p` flag. Falls back to legacy JSON parser if stream result event is missing (known CLI bug)
- Copilot SDK connector: shared `CopilotClient` singleton (lazy-loaded), per-request sessions. Reads `.mcp.json` and converts to SDK format. Emits `assistant.intent` events shown as inline chat bubbles.
- OpenAI-compat connector: calls any OpenAI-compatible API (Ollama, LM Studio, vLLM). Agent loop with MCP tool execution — loads tools from `.mcp.json`, sends as OpenAI `tools` parameter, executes tool_calls against MCP servers in a multi-turn loop. Handles Qwen3/Ollama thinking tokens (`reasoning` field + `<think>` tag stripping). Retries on empty responses (3x with 2s delay).
- MCP tool tracking: tool calls extracted from stream events (stream-json for CLI, session events for SDK), per-tool timing, displayed as child spans in traces waterfall
- Scheduled tasks: cron-style (hour/minute/days) or interval-style (every N ms), timezone-aware
- Watchers: interval-based background monitors (email, calendar, etc.) with dedup via `lastNotifiedIds`
- Watcher email checking: Haiku spawned in muninn's agent home with the bot's `.mcp.json` + `.claude/settings.json` passed explicitly (`--mcp-config` / `--settings`) for Gmail MCP access — see the `MUNINN_AGENT_CWD` row
- Quiet hours: per-user, timezone-aware, overnight ranges supported (e.g. 22-08)
- All timestamps stored as `TIMESTAMPTZ` in DB, exposed as epoch ms in TypeScript

## Logging

Uses [LogTape](https://github.com/dahlia/logtape) for structured logging. **Never use `console.log/warn/error` in `src/` files** — use the logger instead.

```typescript
import { getLog } from "../logging.ts";
const log = getLog("subsystem", "subpath"); // → category ["muninn", "subsystem", "subpath"]
```

**Levels:**
- `log.info(...)` — lifecycle events, request timing, successful operations
- `log.warn(...)` — recoverable issues, fallbacks, deprecations
- `log.error(...)` — failures, exceptions, crashes
- `log.debug(...)` — verbose traces (dedup, user resolution) — only visible when level lowered

**Structured properties** (second argument):
```typescript
log.info("Message from {username}: {preview}", { botName, username, preview: text.slice(0, 80) });
```
- `botName` is special: the console formatter prepends it as `[jarvis]`
- Properties become searchable fields in the JSONL file sink

**Sinks:**
- Console: colored `LEVEL [subsystem/path] message` format
- File: daily-rotating JSONL in `logs/` dir (7-day retention, configurable via `LOG_DIR` env var, set `LOG_DIR=none` to disable)

**Tests:** Unconfigured loggers are silent no-ops — tests never call `setupLogging()`, so all logs are discarded. No mocking needed.

## Database & Migrations
After creating database migrations, always remind the user to run them against the target database. When modifying data models, check if existing data needs to be backfilled or updated — don't assume only new records matter.

## Code Quality
This project is primarily TypeScript. Always ensure code compiles cleanly (`tsc --noEmit` or equivalent) before committing. When fixing TypeScript errors, fix all of them — don't leave partial fixes.
