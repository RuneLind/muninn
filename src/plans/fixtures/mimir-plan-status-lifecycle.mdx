## The design

<Callout tone="info" title="Status and follow-ups are two axes, not one">

The single most common state in this wiki is **"shipped, with a tail"** — nearly every completed campaign leaves pending items, and that is exactly what you cannot see today. A one-dimensional enum collapses it: `shipped` would hide the tail, and a `shipped-with-followups` value would make the enum unfilterable.

So: `plan_status` answers *has it started / is it finished*, and `followups` answers *is anything left over*. The reader filters on both, independently. (Both round-1 reviewers examined this split independently and endorsed it as a correct read of the corpus.)

</Callout>

### Frontmatter contract

```yaml
---
title: …
description: …
tags: [muninn, plan, …]
plan_status: shipped
status_date: 2026-07-30
followups: open
status_note: "PRs 1–4 of 6 landed; 5 and 6 gated on the soak (muninn #399)."
---
```

| Field | Required | Meaning |
|---|---|---|
| `plan_status` | yes, on `plans/*.{md,mdx}` | The lifecycle value — enum below. |
| `status_date` | yes, except on `proposed` | ISO day the status last **changed**. |
| `followups` | no (absent ⇒ `none`) | `open` \| `none`. |
| `status_note` | no | One line of free prose. **Must be quoted** — see the trap below. |

<Callout tone="warn" title="Why the key is `plan_status`, not `status`">

`status` is already taken by a **registered wiki**. `melosys-kode-wiki` (mounted via `WIKI_EXTRA`) carries `status:` on **75 pages** with an unrelated vocabulary — `untracked` (21), `deleted-from-source` (9), `resolved`, `open-proposal`, `implemented`, `complete`, `in-progress`, `tracked`, `todo`, and free prose. Taking the bare `status` key would have hijacked it: the facet would have appeared on the nav wiki showing one valid value out of 75, with ~74 pages failing validation on every 5-minute index rebuild.

Namespacing to `plan_status` also means mimir's 11 existing free-prose `status:` values (PR numbers, commit SHAs) **do not collide and are not overwritten** — they are real content, and step D0 folds them into the body before the bare key is removed from `plans/`.

</Callout>

`plan_status` values, deliberately few:

| Value | Means |
|---|---|
| `proposed` | Written; awaiting go/no-go. |
| `ready` | Reviewed / plan-review-looped; safe to dispatch. |
| `in-flight` | Actively executing. |
| `blocked` | Waiting on something external (a subscription, a customer, another repo). |
| `shipped` | All planned work landed. |
| `superseded` | Replaced by another plan — pair with a wikilink in `status_note`. |
| `abandoned` | Won't do. |

`ready` earns its own value: the plan-review-loop is a real gate here, and "hardened, just needs a session" is the state you most want to filter for when picking work.

<Callout tone="bad" title="Frontmatter trap — quote anything containing `#`">

muninn's `parseFrontmatter` is a bespoke YAML *subset*, not YAML: it takes the rest of the line verbatim and strips no comments. Standard YAML (gray-matter, which mimir's own MDX pipeline uses, and Obsidian) reads an unquoted `#` as a comment and truncates the value. `status_note: muninn #399 open` therefore means two different things to two parsers — the exact bug lint check 7 exists to catch for `accent:`.

So: `status_note` **must** be quoted, and check 8 validates it. A `[[wikilink]]` in a note becomes a real graph edge (`extractWikilinks` reads the whole file, frontmatter included) — desirable for `superseded`, but stated rather than discovered.

</Callout>

### Migrate the prose, then generate `plans/index.md`

This is the load-bearing half, and the destructive one. `plans/index.md` is **87 KB / 124 entry bullets** (119 of them linked) of hand-written synthesis — PR numbers, commit SHAs, dispositions, cross-links, much of it existing nowhere else. Entries average ~700 characters and run past 1.2 kB. `status_note` is one line. **A regenerate without migration is an uncompensated deletion of the wiki's densest page**, and the flow is self-consuming: `propose-plan-status.ts` reads that same prose as its inference signal.

So the order is fixed, and **D0 gates everything after it**:

- **D0 — snapshot.** Copy the current `plans/index.md` to `archive/mimir/2026-07-30-plans-index-pre-generation.md` with the literal `signal: none` + a `signal-reason:` line — check 1's escape hatch greps for exactly `^signal: none`, so any other value leaves the snapshot permanently flagged. Committed before anything else runs. The disposition queue survives regardless of what follows.
- **D1 — fold.** For each plan, append its index-entry prose into the plan's own body as a `## Catalog note` section, and fold any existing free-prose `status:` value in with it. Then remove the bare `status:` key from `plans/` so `plan_status` is the single authority there.
- **D2 — verify the fold.** A script diffs the set of entry texts against the plan bodies and **fails on any text not found** — except entries the sidecar owns (below), which it is given explicitly so it does not fail by construction. It must **also** assert that each of the 11 free-prose `status:` values D1 removes survives in its plan's body: those carry PR numbers and SHAs found nowhere else (`huginn-indexing-job-observability.md`'s alone names three PRs and three commits), and nothing else gates their deletion. Named acceptance: *no unique index prose and no removed `status:` value is lost.*
- **D3 — backfill** `plan_status` / `status_date` / `followups` from the reviewed TSV.
- **D4 — generate** and only then land check 9. The generator's **section mapping is fixed, not left to the implementer** (check 9 is a byte-diff — two implementers guessing differently is a hard failure): `shipped` / `abandoned` / `superseded` → `## Done`; `proposed` / `ready` / `in-flight` / `blocked` → `## Active`; sidecar rows use their own `section` field. The `## Status legend` block is **regenerated from the `plan_status` enum**, replacing today's five-value legend that nothing uses.

The generator reads `plans/*.{md,mdx}` frontmatter — but the index it replaces contains more than that:

- **4 `.html` + 1 `.txt`** in `plans/`, all currently listed, and lint **check 2 explicitly globs `plans/*.html`**. Without rows for these, the freshly generated index fails check 2 on day one while passing check 9.
- **4 bullets whose primary link points outside `plans/`** (all `../archive/…`) — one of them under `## Active`. Inline `../blogs/…` links inside entry prose are secondary and need no row.
- **5 struck-through retired entries under `## Active`** whose title carries **no link at all** (`plans/index.md:56–62`) — ~3.5 kB of real synthesis with no `plans/` file to fold into and nothing for a frontmatter scan to emit.

All **14** of these are carried by a small hand-maintained **sidecar** the generator splices in (`plans/index-extra.yaml`: title, href, section, note, optional `plan_status`). D1 is told the same list so it does not look for a plan body that does not exist; D2 is told it so it does not fail on their prose. The sidecar's `plan_status` is **index-only and unreachable by the reader facet** — `buildExplainerMeta` hardcodes `type: "explainer"` for `.html` and check 8 excludes non-markdown, so these rows can never carry a reader-visible status. Stated rather than left to contradict the "one authority per location" rule.

`scripts/lint.sh` gains a `--check` byte-diff modelled on the MDX pipeline's check 6, guarded on **`command -v bun` only** so `lint.sh` stays standalone-runnable. Deliberately *not* check 6's full guard: that also requires `scripts/mdx-explainer/node_modules`, which exists because `build.ts` needs puppeteer/Chromium for mermaid. `build-plans-index.ts` and `lastNonSweepTouch()` have no third-party deps, and reusing the full guard would silently SKIP the campaign's two core checks on any clone that hasn't run `bun install` in an unrelated directory.

**The generated file must announce itself — but not as an HTML comment.** `plans/index.md` is a real reader page (`buildWikiIndex` globs `**/*.{md,mdx,html}` with no index exclusion), and `formatWebHtml` escapes anything it doesn't recognize, so a `<!-- generated by … -->` line 1 renders as visible literal text at the top of the article — the same bug class `render.ts` already had to add a line-stripper for with the fact-check sentinels. The `<!-- generated from` precedent is safe only because it lives in `.html` explainers. So the banner uses the existing italic-subtitle convention instead:

```markdown
_Generated by `bun scripts/build-plans-index.ts` — do not edit. Set `plan_status` in the plan's frontmatter and re-run._
```

Check 9's failure message prints that same command. Without this the only signal that a hand edit is wrong is a lint failure the editor may never run — mimir's `CLAUDE.md` carries **no `plans/index.md` maintenance rule at all** today (its index rules are about the *root* `index.md`). PR E adds one, carrying the regenerate command too.

**Regeneration is manual; lint is the only backstop.** There is no git hook, no CI (mimir has neither today) and no scheduled run in this campaign's scope. A newly created plan therefore reds check 9 until someone runs `lint.sh`. That is a deliberate v1 limit — stated plainly so "kept accurate automatically" is not read as more than it is. A pre-commit hook is the obvious follow-up and is explicitly **not** in PRs A–F.

<Callout tone="info" title="Decision: a generated index, not no index">

The simplest alternative is to delete `plans/index.md` entirely and let the reader's facet be the only catalog — the same argument this plan makes for retiring `mimir-product-priorities.md`. Declined for one concrete reason: **the reader is loopback-only** (`DASHBOARD_HOST` defaults to `127.0.0.1`) and requires muninn running, while `plans/index.md` is readable on GitHub, in Obsidian, and by any agent with a filesystem. A generated index keeps that reach at near-zero maintenance cost. If the reader ever becomes the only way anyone browses mimir, revisit.

</Callout>

### Backfill

145 files need a status. Not an LLM sweep — a script proposes, a human confirms.

`scripts/propose-plan-status.ts` emits a reviewable TSV with **three** inferred columns (`plan_status`, `followups`, `status_date`) from the signals that already exist:

- the index entry's emoji and SHIPPED/EXECUTED/not-started phrasing;
- the plan file's own first Callout title or bold `Status:` line;
- **last non-sweep git touch** — defined as the last commit touching the file that modified **fewer than 10** files under `plans/`. This matters: a single 2026-07-08 frontmatter sweep (`3575dc6`) is the last commit for **62 of the 145** plans, so naive git recency reports "22 days ago" for work that shipped in April and for work that is live today. The naive signal is dead for 43% of the corpus.

`status_date` inference chain, in order: a date named in the plan's own status prose → last non-sweep commit date → frontmatter `updated`/`created` → today, **flagged for review**. Check 8 tolerates an absent `status_date` only on `plan_status: proposed`.

Expect the inference to be right on the ~39 obviously-shipped and the ~15 obviously-not-started, and to need real judgement on the ~30 dormant middle — the disposition queue above, done once. The `proposed` / `ready` distinction is **not** mechanically inferable; the script emits `proposed` for both and the TSV review promotes.

### Reconcile with the conventions already here

Two existing conventions overlap and must be squared in **PR E**:

- **`verified-status:`** (`CLAUDE.md`, archive conventions) — `accurate | resolved | open-proposal | superseded | obsolete | uncertain`. `superseded` appears in both enums with different meanings. Rule: `plan_status` governs a page while it lives in `plans/`; on retirement to `archive/<project>/` the page **drops `plan_status` and gains `verified-status`**, mapped `shipped → resolved`, `abandoned → obsolete`, `superseded → superseded`, `proposed`/`ready` → `open-proposal` **when commits or a feature/draft-PR branch exist, else `obsolete`** (PR E's reviewer found the unqualified mapping contradicted `open-proposal`'s own commits-exist definition; the qualified form is what `CLAUDE.md` carries). (`in-flight` and `blocked` are not retirable states — nothing maps them.) One authority per location.
- **`last_verified:`** — proposed by `mimir-wiki-improvements-2026-07.md` Angle 2, never adopted. `status_date` supersedes it for `plans/`; that plan is marked `plan_status: superseded` by this one — the first live use of the new enum.

`~/.claude/skills/mdx-explainer/SKILL.md` gains the contract, and its doc-type table's Plan row states a new plan is created `plan_status: proposed`.

## My take, and what else to fix

**The status field is the smaller half.** The real defect is that plan status is maintained in two places and neither is authoritative — the file says one thing, the catalog another, both prose. Adding a third would make it worse. Generating `plans/index.md` from frontmatter is what closes it, which is why PR C+D matter more than PR B. The 2026-07-07 manual triage that drifted back within three weeks is the proof.

**`plans/` has no retirement rule and has become an append-only pile.** 145 markdown plans, of which perhaps 20 are live work, against a `CLAUDE.md` that says plans hold "active/in-flight work… kept outside the wiki so ephemeral planning doesn't pollute the durable knowledge base". That contract is broken by volume alone. PR F is the fix, and it is deliberately **deferred out of this campaign** — it changes what `archive/` means and interacts with the `verified-status` mapping above, which deserves its own decision rather than riding along.

**The live status tracker is currently outside the wiki.** `~/.claude/projects/…/memory/MEMORY.md` carries genuinely accurate per-project status with explicit PENDING items — doing the job `plans/index.md` claims to do, per-machine and invisible to the reader. Once `followups` exists in frontmatter, that content should flow into the plans it describes; the memory index keeps the pointers, the wiki keeps the state.

**Accepted consequence — the mtime flood.** mimir's pages carry almost no frontmatter dates, so the reader's "Recently updated" key is effectively file mtime (`pageTimeMs` takes the *larger* of mtime and any frontmatter date, so adding a truthful `updated:` cannot rescue it). Rewriting 145 plans in one sweep makes every plan the newest page in the wiki, and the Timeline tab and picker freshness label inherit it. This is self-healing as other pages are touched, and "Recently added" (birthtime-based) is unaffected. Stated here so it is not filed as a regression.

**Two smaller ones worth folding in:**

- `mimir-product-priorities.md` self-declares "⚠ Stale as of…" and is the designated "read this when picking a session topic" page. Once the reader can filter `plan_status: ready`, the facet does its job — retire it rather than maintain it.
- The past-due `~date` obligations lint already reports have been ignored because check 4's output is buried under checks 1 and 2's noise. Fixing 1 and 2 makes 4 visible again — though note that is *visibility*, not coverage; the `.mdx` extension is what makes it complete.

**What I would not do:** don't add a per-plan progress percentage or a PR-count rollup. The PR numbers in these plans are already prose and would need a GitHub round-trip to stay true — a field that goes stale silently is worse than no field, which is the exact lesson of the current `plans/index.md`.
