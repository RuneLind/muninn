# Dashboard Module — Architecture & Rules

## File Overview

| File | Role |
|---|---|
| `routes.ts` | Creates Hono sub-router, registers all route modules. Also mounts `GET /api/attention` inline — the home "Attention" surface (stale watchers / pending gardener drafts / failed recent runs). Assembly is the pure, injectable `src/dashboard/home-attention.ts` (`assembleAttention`, mirrors the agents/models/indexing assembler pattern); never 5xx (degraded sources → `errors[]`). Stale-watcher detection is `isWatcherStale` — `lastRunAt + 2×intervalMs < now`, but the effective interval is floored at 1 day for **hour-gated** watchers (a short interval is only a floor there; without the floor, e.g. a 5-min-interval daily digest reads permanently stale). The gardener-drafts source is TWO seams: `getDraftCounts` (per-bot `countDraftWikiProposals`) AND `getWikiDraftCounts` (per gardener-capable standalone `WIKI_EXTRA` wiki via `countDraftWikiProposalsByWiki` — the consolidation-gardener's `synthesis` proposals are keyed by `wiki_name`, invisible to the bot-keyed count; surfaced as a `gardener_drafts` item with a `?wiki=<name>` review link). |
| `openapi-spec.ts` | OpenAPI 3.1.0 spec covering all JSON API endpoints |
| `index.ts` | Barrel export: `createDashboardRoutes` |

> **Moved out (2026-06, layering cleanup):** the `activity-log` and `agent-status` singletons now live in `src/observability/` (they are imported by core/scheduler/watchers, not just the dashboard — see `src/observability/CLAUDE.md`). ## Route Organization

Routes are split by domain in `routes/`:

| File | Endpoints |
|---|---|
| `data-routes.ts` | Main CRUD: messages, memories, goals, tasks, watchers, users, threads, connectors |
| `sse-routes.ts` | SSE streams on `/api/events`: `activity`, `stats`, `agent_status` (phase), `request_progress` (single-pane waterfall), and `agent_runs` (full snapshot of ALL AgentRuns for `/agents` — initial via `agentStatus.getAll()`, live via `subscribeAll`, throttled ~1/s in the tracker, tools capped at 20 per run) |
| `agents-routes.ts` | `/agents` live-agent dashboard page + `GET /api/agents/overview` (JSON: `running` + `upNext` + `recent`). Assembly is the pure, injectable `src/dashboard/agents-overview.ts` (`assembleAgentsOverview`). `running` from the AgentRun registry; `upNext` from `scheduled_tasks.next_run_at` + watchers (next fire mirrors `isScheduledTimeDue` — time-of-day slot dominates a naive `last_run_at + interval`; `computeWatcherNextRun`); `recent` is a four-source UNION keyed by span NAME (chat `%_message`/`telegram_voice` roots + `watcher:%` child spans via `src/db/agent-activity.ts`, extractor `haiku_usage` rows, and the registry completed-runs ring for gardener_drain/capture/research/per-task only — per-kind source-of-truth prevents double-counting). The payload also carries `estimates` — per-live-run `expectedDurationMs` keyed by `estimateIdentity(kind, name)` (`src/dashboard/agent-eta.ts`; watcher identities sourced from durable `watcher:<type>` span durations via `getWatcherRunDurations`, every other kind from the in-memory completed-runs ring, chat NEVER estimated, median of the last ~20) — and `processStartedAt` (the "history resets on restart" empty-state). The SSE `agent_runs` cards carry no estimate; the `/agents` client looks each live run up in `estimates` and computes pace (`elapsed/done × total`) locally where a gardener drain reports discrete progress (pace beats the history median). Never 5xx — degraded sources land in `errors[]` (a degraded `watcher_durations` just drops watcher estimates → elapsed-only). |
| `traces-routes.ts` | Trace spans: list, detail, waterfall data, cleanup |
| `search-routes.ts` | Knowledge base document search and management |
| `research-routes.ts` | `/research` page: cited Q&A over the shelf corpus (`GET /api/research/ask` SSE — retrieve via `researchKnowledge`, synthesize one cited answer; see `src/research/{corpus,answer,ask}.ts`) + the browse `/api/research/*` endpoints. Also the Jira research flow (`/api/research/chat`: trigger analysis, post to chat). |
| `memsearch-routes.ts` | Memory semantic search (hybrid FTS + vector) |
| `graph-routes.ts` | Knowledge graph page + wikilink edge extraction across knowledge collections |
| `wiki-routes.ts` | `/wiki` reader page + `/api/wiki/{pages,page,html,ask,explain,factcheck,digest,atlas}` (per-bot knowledge-wiki browser). **`GET /api/wiki/atlas`** serves the Atlas tab projection (`projectAtlas`); with **`?semantic=1`** and a wiki that has `collections`, it also attaches a `semantic` overlay — huginn per-collection similarity graphs (`top_k=6`, `min_similarity=0.9`) unioned by the pure `joinSemantic` (`src/wiki/atlas-semantic.ts`): `edges` (full-index-resolved, max-sim deduped), namespaced `communities` (`<collection>:<id>` — per-collection Louvain ids restart at 0), `nodeCommunity` (first collection in `collections` order wins overlaps), `nodeType`/`nodeTags` (badge/label info for pages capped out of the rendered columns). Huginn ids match index pages on the NFC-folded `coverageKey` but emit on bare `normalizeRelPath`. Degrade is the contract: huginn unreachable / non-200 / no collections ⇒ no `semantic` field, HTTP 200, payload otherwise untouched; per-collection fetches run concurrently under one ~2.5s deadline; full-success unions cache 5 min per wiki (non-sticky degrade — failures never cache). The client (`views/components/wiki-atlas.ts` + pure helpers in `wiki-atlas-semantic.ts`) renders community dots + a rendered-pill-gated legend with dim-others, dashed semantic edges on selection (threshold slider 0.90–0.995 default 0.98, "+N similar not shown" for capped-out neighbors, toggle default OFF with eager fetch), and the collapsible "Clusters at threshold" rail — client-side union-find over the FULL graph, ≥3-member components, >40-member blob guard, synthesis-candidate badge (≥3 narrative-type members, 0 synthesis-type, via `CLUSTER_ROLE_BY_TYPE`). The per-collection fetch/deadline/TTL-cache orchestration (`getSemanticOverlay`, `fetchSimilarityGraph`) was **extracted to `src/wiki/atlas-semantic.ts`** alongside `joinSemantic` so the consolidation gardener reuses it; the atlas route just calls it (byte-identical behaviour). **Consolidation gardener — Draft synthesis (PR 2):** a `candidate` rail cluster carries a **Draft synthesis** button → `POST /api/wiki/atlas/draft-synthesis` `{wiki, members[], label}`, which NEVER trusts the client badge — it resolves the members in the wiki index, rebuilds a FRESH overlay, and re-runs `computeClusters` (`confirmSynthesisCandidate`, scanning thresholds MAX→MIN) to reconfirm the members are a candidate; a cheap raw `> RAIL_BLOB_MAX` guard rejects oversized payloads early. Dedup on live-OR-applied topic_keys (`getLiveOrAppliedTopicKeysByWiki`, matching the GET's pending-mark so an APPLIED topic also 409s a re-POST) → 409 `{state:"pending"}`; a second draft in flight for the same wiki+topic → 409 `{state:"running"}`; ANY draft in flight for the same wiki (per-wiki single-flight, v1 contract — closes the label-drift double-spend) → 409 `{state:"running"}`; unknown wiki 404; collection-less wiki → clean 400 like Ask. On success the draft runs **DETACHED** (respond `{state:"started"}`, `/agents` visibility via the traced one-shot) through `src/gardener/synthesis-drafter.ts` (`draftAndPersistSynthesis`): harvest bounded member excerpts → saga-style prompt → traced `consolidation:draft` one-shot on the resolved synthesis bot (`resolveWikiSynthesisBot`, 8k thinking cap, never bare `executeOneShot`) → BESPOKE `synthesisShapeGate` (frontmatter `type: blog`, confined under `blogs/`, EVERY member wikilinked — shares only `isPathConfined`/`containBodyLinks` with `draft.ts`) → persist a `synthesis` proposal keyed to the wiki (`wiki_name`, `bot_name` = the truthful synthesis bot, `related_pages` = members for apply-time See-also wiring). The GET atlas response also carries `semantic.pendingSynthesisTopics` (`getLiveOrAppliedTopicKeysByWiki`, attached OUTSIDE the cached overlay) so a cluster whose `synthesisTopicKey(label)` already has a live/applied proposal renders a "proposal pending → gate" link instead of the button. The client rail renders the Draft control from module-level per-topic sets (NOT mutated button DOM), so a threshold-slider / Types↔Months re-render preserves state: `draftingTopics` (a disabled "drafting…" button), `retryTopics` (a "retry draft" button + aria-label, the non-color a11y cue), else the active button. A POST does NOT optimistically mark pending — it starts one shared bounded reconcile poll (5s, ~3min) that re-reads `semantic.pendingSynthesisTopics` and promotes the topic to pending when its proposal persists, or drops it to retry on timeout; the click-time topicKey is re-stamped onto recomputed clusters (`RailCluster.synthesisKey`) so a label drift can't strand the state. `synthesisTopicKey` lives in the import-safe `wiki-atlas-semantic.ts` (client rail + server share it — slug parity). `/api/wiki/explain` (SSE) is **Select-to-Explain**: a sibling of `/api/wiki/ask` that takes a reader-selected passage (`sel`) on a page (`page`) and runs the SAME research pipeline (retrieval over the wiki's `collections` → coverage gate → cited synthesis → `answer_html`) through `streamResearchSSE`, with a per-wiki system prompt carrying the passage's article context (excerpt located in the body via a markup-tolerant locator + the wiki's Similar titles as background). Both markdown and HTML **explainer** pages are supported: an explainer body is reduced to prose via `htmlToText` (`src/wiki/explain-context.ts`) before the same locator runs (explainer selections reach the pill via the injected iframe bridge, below). All prompt/context assembly is the pure `src/wiki/explain-context.ts` (`buildExplainAskOptions`); the preflight decision chain is the exported pure `resolveExplainPreflight` (in `wiki-routes.ts`); the Similar fetch is the shared `fetchSimilarPages` (`src/wiki/similar.ts`, timeout-bounded here so it can't stall the stream open). Same never-5xx contract as Ask (400 JSON for missing `sel`/`page`; wiki/page problems as `app_error`). **Client (PR 2; rail redesign PR 4):** selecting text in a rendered markdown article reveals an "✨ Explain" button in the breadcrumb bar above the article (`wiki-browser.ts` — `renderBreadcrumb` renders it hidden per page, shown only while a selection exists; styled in `wiki-page.ts`. The pre-PR4 floating pill / `positionExplainPill` are gone — the button lives in a stable spot, no page-scroll math); activating it runs the explain stream through the shared `runAskStream` (the Ask runner, extracted so Ask + Explain share supersede/buffer-reset/SSE handling) — which auto-switches the right rail to the **Ask tab** (`switchConnTab("ask")`; the Connections/Ask tab pair, removed in PR 4, was restored afterward because the pinned Ask ate the rail and left Similar below the fold) — so the explanation lands in the article pane + session history like any Ask turn. Pure label/URL helpers live in the import-safe `wiki-explain.ts` (unit-tested). **Fact check (`/api/wiki/factcheck`, SSE):** a sibling of Explain that web-verifies a page's factual claims — selection-scoped (`mode=sel`, reusing the same `renderBreadcrumb` selection state as Explain — a "✓ Fact check" button beside "✨ Explain") or whole-article (`mode=article`, an always-visible "🔎 Fact check" breadcrumb button on markdown pages AND explainers). Unlike Explain it runs **NO retrieval and NO coverage gate** — a dedicated `streamFactcheckSSE` (`routes/factcheck-sse.ts`, sibling of `research-sse.ts`; `streamResearchSSE`/`streamResearchAnswer` are byte-untouched) runs a **THREE-phase** pipeline: (1) **claim extraction** — `callHaikuWithFallback` over the capped article body / the selected passage, parsed by the pure `parseClaimList` (null ⇒ a clean `app_error`), emits a `claims` SSE event `{claims:[{index,title}]}`; (2) **bounded-parallel verification** — an inline `FACTCHECK_CLAIM_CONCURRENCY`(=2) worker pool (`runClaimPool`, pure/injectable/unit-tested) over per-claim tool-enabled `executeOneShot` calls (each 90s `FACTCHECK_CLAIM_TIMEOUT_MS`, R1's one-block output), each emitting a `claim_result` `{index,verdict,markdown}` (verdicts ✅/⚠️/❌/❓); (3) **compose** (multi-claim only) — a small `executeOneShot` (`thinkingMaxTokens:0`, `timeoutMs:COMPOSE_BUDGET_MS`; tools stay available — NOT disabled — a stray tool excursion just burns the compose budget and degrades to the neutral header) writing the overall-assessment lede, whose deltas DO stream via `text_delta`→`delta` (nothing else running); the server assembles `lede + blocks` (`assembleFactcheckAnswer`). **Deadline:** the pool checks `Date.now()` against `deadline = start + FACTCHECK_TIMEOUT_MS − COMPOSE_BUDGET_MS` (and the `clientGone` flag, also set by `stream.onAbort`) BEFORE launching each claim; not-launched claims emit a synthetic ❓ "skipped" block (excluded from the count). For N=1 (a single-fact selection) there is NO compose and NO live verdict deltas — the lone block arrives whole via `claim_result` (accepted tradeoff). **Live tool progress:** each verify call's `onProgress` forwards `tool_start`/`tool_end` as SSE `tool` events (with a `claimIndex`, behind the same `clientGone` write-guard) — text deltas are NOT forwarded during the fan-out (index-less parallel deltas would interleave) — `start` carries a server-computed `{label, detail}` from `getToolProgress` (`src/ai/tool-status.ts` — WebSearch→"Searching the web" + query, WebFetch→"Reading" + `www.`-stripped hostname, tolerant of a clipped URL; a clean label/detail SPLIT so the client doesn't double-parse a composed string), `end` just `{name}`. The client's `tool` listener (fact-check turns only) drives the status line and accumulates deduped WebFetch hostnames into `turn.toolSources` — a persisted "Consulting: host · host" chip row on the turn (round-trips through `wiki-ask-session.ts` as an optional string array). Each chip is an `<a target="_blank" rel="noopener">` (factcheck-v3-sources): the `tool` event also forwards the full `url` (`rawUrlField`), and the client keeps the FIRST full URL seen per host in a `toolSourceUrls` map (host→url) to build the href; hostname stays the dedup key + chip label. The map is **persisted** (round-trips through `wiki-ask-session.ts` as an optional host→url record, shape-validated in `isValidTurn`: a malformed map is dropped but the turn kept), so a rehydrated chip keeps its real deep-link; a pre-PR turn / dropped map degrades to `https://<host>/`. The per-claim verify `Sources:` line is now emitted as markdown links (`[hostname](url)` — the prompt contract in `factcheck-context.ts`) with a belt-and-suspenders pure fallback `linkifySourcesLines` (factcheck-only, in `factcheck-sse.ts`, applied inside `assembleFactcheckAnswer`) that wraps any remaining bare URL on a `Sources:` line — the shared `web-format.ts` deliberately has NO global bare-URL autolinker. Ask/Explain never emit `tool` (only `factcheck-sse.ts` forwards it; `research-sse.ts` is byte-untouched). Corpus-independent, so it needs NO `collections` but DOES need a **web-tools connector** (`connectorCapabilities().supportsWebTools` — `claude-cli`/`claude-sdk` only; a Copilot/OpenAI-compat bot preflights out with a clean `app_error`). Raised `FACTCHECK_TIMEOUT_MS` (280s) and a `FACTCHECK_MAX_CLAIMS` (8) cap sized to the measured ~15s/web-verified-claim. Traced under one `factcheck` root — an `extract` span (Haiku, + `haiku_usage` row via the threaded tracer), one indexed `claude:claim-<i>` span per verify (concurrent `start("claude")` would clobber a shared label; WebFetch tool child spans attached via `attachToolSpans(…, "claude:claim-<i>")` — the optional 4th `parentLabel`), and a `compose` span — and registered as a `factcheck` `/agents` run (`RING_RECENT_KINDS`) with phases `extracting_claims`→`verifying_claims` + per-claim `updateProgress`. All prompt/context assembly (extraction / per-claim verify / compose prompts, prior-block sentinel strip `<!-- factcheck:start/end -->`, `parseClaimList`) is the pure `src/wiki/factcheck-context.ts` (`buildClaimExtractionPrompt`/`buildClaimVerifyPrompt`/`buildComposePrompt`, unit-tested); the route only reduces the body (`htmlToText` for explainers) + computes the base hash, and the SSE builds the prompts at runtime. Client: both buttons call the shared `runAskStream` against the factcheck URL, so verdicts land in the article pane + `askTurns` like any Ask/Explain turn — flagged `kind: "factcheck"` (drives the "Checked N claims against the web" status line + gates the ➕ button), with the `done` payload's `claimCount` (only real verify blocks — synthetic ❓ skips excluded) + `baseHash` (page-content sha256) + `bodyLen` (the pinned `integrateBodyLen` referent, **omitted entirely for explainer pages** — they are HTML on disk and can never be integrated, so an HTML byte count would be a number nothing enforces) + the checked page's `name`/`type` stored on the turn. The `claims` handler seeds a per-turn checklist (`n. ☐ <title>`, transient/not persisted), `claim_result` swaps each row for its verdict block, and a multi-claim turn's compose deltas accumulate into a separate `composeText` lede rebuilt above the blocks (`rebuildFactcheckBuffer`); once total > 1 the claim counter OWNS the status line (per-tool flips suppressed). Pure URL/label helpers `buildFactcheckUrl`/`factcheckLabel` in `wiki-explain.ts`. **➕ Add to article (`POST /api/wiki/factcheck/append`):** a plain JSON route (normal REST semantics — 400 missing `page`/`answer`/`baseHash` · 404 unknown wiki/page · **400 explainer-page reject** (markdown-only — appending a callout to a standalone `.html` would corrupt it) · 409 stale `baseHash` · 200 `{written, page}` — but the whole body is wrapped so an unexpected failure returns 500 JSON, mirroring `POST /api/wiki/remember`) that persists a fact-check answer as a `> [!factcheck]` Obsidian callout (`buildFactcheckBlock`, tone `info` via the render.ts `calloutTone` map — no fifth style) fenced by the `<!-- factcheck:start/end -->` sentinels. Writes via the DEDICATED `appendBlockToPage` helper (`src/wiki/append-block.ts`, unit-tested) — NOT the gardener `applyWikiProposal` path (which would run containBodyLinks + alias-strip over the whole page): confinement (`isPathConfined`) → **raw-bytes** `sha256` staleness vs `baseHash` (same convention as the factcheck route; a mismatch is 409, NOT mtime — an append changes the raw content, so an older turn's baseHash correctly goes stale) → `spliceSentinelBlock` (REPLACE an existing block in place, else insert before a trailing `## Sources`, else append at end) → `Bun.write` → `insertLogEntry` into log.md → refresh the wiki index cache → fire-and-forget huginn reindex over the wiki REGISTRY entry's `collections` (NOT `reindexCollectionFor`, hardcoded to jarvis's wiki/wiki-life; no collections ⇒ skip reindex, still write + log). Allowed on ANY registered wiki's markdown pages. Client: the button renders ONLY on committed fact-check turns whose `pageType !== "explainer"` (hidden entirely for explainer checks), delegated at the document level (the pane re-renders per turn) and gated on the turn being committed like the follow-up/Remember bars; success swaps to a non-interactive "✓ Added to article" + reloads the page in the reader so the callout is visible; 409 shows a "page changed — re-run the fact check" message. **Integrate into article (factcheck v4, PR 1 = backend):** the second write action on a fact-check turn — instead of appending a callout it EDITS THE PROSE in place from a structured edit list. Two plain-JSON routes, same never-throw wrapper as append. `POST /api/wiki/factcheck/integrate` `{wiki, page, answer, baseHash}` **proposes**: baseHash CAS FIRST (409 `{error, stale:true}`), markdown-only (explainers 400), body cap `INTEGRATE_BODY_MAX` (24k) → 400 "page too long to integrate", claim anchors parsed SERVER-SIDE out of the posted `answer` via `correctableClaims` (the `### <emoji> Claim n/m — <title>` heading contract; VS16-tolerant on ALL four emoji, `—`/`–`/`-`/`:` separators, case-insensitive `claim`; ❌/⚠️ only — ✅/❓ untouched in v1). NB the `answer` is CLIENT-POSTED: server-side parsing buys formatting robustness and ONE implementation of the heading contract, **not** trust — a caller that can post an answer can post any verdict blocks, which is why every edit is previewed, bounded and CAS-guarded, then ONE fenced one-shot on `resolveWikiSynthesisBot` (no bot ⇒ 409) returning `{"edits":[{claimIndex, verdict, old, new, reason}], "note"}`. It NEVER writes; the response is `{edits (range-resolved, with `start`/`end`/`tier`/`resolvedText`/`beforeCtx`/`afterCtx` — `resolvedText` is the RAW slice that will actually be replaced, which a tier-2 rescue makes differ from the model's `old`), dropped:[{edit, reason}], note, budget}` — zero surviving edits is a valid 200. `dropped` carries EVERY rejection: the model's own malformed items (`parseEditList`), the count/size caps, the unresolvable anchors, AND the propose-time **ratio budget** (`enforceChangeBudget`, greedy in edit order over the RESOLVED spans) — so accept-all can never be a guaranteed 400 at apply. Reserved basenames (log/index/CLAUDE, either extension) 400 at BOTH routes via `hasForbiddenBasename`, before the one-shot is spent. `POST …/integrate/apply` `{wiki, page, edits, baseHash}` **applies** the client-echoed accepted edits (stateless; apply deliberately trusts the payload — auth-less loopback — but bounds it HARD: ≤`INTEGRATE_MAX_EDITS` 12, ≤`INTEGRATE_MAX_EDIT_CHARS` 2000 per old/new, total changed chars ≤ `max(0.25 × bodyLen, 2000)`; any breach ⇒ 400 NAMING the bound — the changed-chars bound is measured ONLY INSIDE the write section on the freshly-resolved spans (there is deliberately NO cheap pre-resolution ratio gate: the payload sum `Σ max(old,new)` is not a bound in either direction — a tier-2 span can exceed `old.length`, while an `old` carrying reflowed whitespace OVER-counts it and would falsely 400 a set propose approved); `INTEGRATE_BODY_MAX` is re-checked here too, and a path-confinement rejection maps to 400 not 500), returning `{applied, dropped, page, committed, reason?}`. `coerceClientEdits` is held at parity with `parseEditList` — blank `old` and EMPTY `new` both rejected (an empty `new` is a silent deletion), bare ⚠ normalized, `reason` trimmed, and injected `factcheck:start/end` sentinels neutralized in every `new` at BOTH entry points. **The pure engine is `src/wiki/integrate-edits.ts`** (the test seam): TWO masks over the body, never fused — `matchMaskBody` is SAME-LENGTH (each excluded code unit → one U+E000 `ZONE_SENTINEL`; region removal would splice text into adjacency and let a phantom `old` match across the seam; NUL is forbidden by defensive invariant since `Bun.spawn` rejects it in argv) and drives all offset math, while `promptMaskBody` collapses each zone to a readable placeholder for the model. Zones = frontmatter · `factcheck:start/end` blocks · fenced code (``` AND ~~~, marker-matched with a CommonMark closer-length rule (the closing run must be ≥ the opener's, so a ``` line inside a ````-opened block is content, not a closer), and scanned only OUTSIDE the frontmatter/sentinel zones so a stray ``` quoted inside a persisted fact-check block can't invert fence parity for the rest of the page; INDENTED code blocks are deliberately left editable) · (on `.mdx`) **BLOCK**-component TAG MARKUP ONLY, line-anchored and derived from markdown-ast's shared `COMPONENT_TAG_SOURCE_SINGLE_LINE` — the newline-free attribute-tail variant, so a tag missing its `>` can't swallow the prose below it up to the next `>` anywhere in the page; the leading-indent allowance is deliberate since `tryParseComponent` matches the TRIMMED line (inner prose stays editable; INLINE tags and prose mentions of a component are deliberately NOT masked — masking them made every sentence containing one permanently unintegrable with a misleading "no longer found" reason). `integrateBodyLen` is the ONE pinned body-length referent — the factcheck `done` SSE payload's new additive `bodyLen` and the integrate route's cap check both call it, so a code-heavy page can't have the client budget against a number the server never enforces. `applyEdits` resolves all ranges against the ORIGINAL masked body (exact unique match, else a tier-2 whitespace-COLLAPSED retry mapped back through `collapseWithMap` — now exported from `explain-context.ts`; 0 or ≥2 matches ⇒ dropped, never fuzzy-applied). The tier-2 rescue is GATED by `collapsedRescueRisk`: `collapseWithMap` also strips `*`/`_`/backtick and rewrites `[label](url)` → `label`, so a mapped-back range can start after an opening delimiter while consuming the closing one (`**NEW`), eat a link's URL (`See [NEW here.`) or span a paragraph break — a rescued range whose raw slice contains a paragraph break (`\n[ \t\r]*\n` — a bare `\n\n` test misses CRLF pages), whose delimiter counts differ from `old`'s, or whose EDGE sits offset inside markup (the count check alone is invariant under a ONE-DELIMITER SHIFT: `[Claude 3](url-a) before GPT-4o` maps back to a slice with identical counts that splices in the OTHER link's URL — so each edge is boundary-tested against the body char just outside it) is REJECTED with an honest reason rather than spliced, rejects overlaps (earlier wins), then splices DESCENDING by start offset — no `String.replace` and deliberately no per-edit re-validation mid-apply. `parseEditList` validates to null (a malformed response ⇒ 502, never a write) and reports per-ITEM failures as `dropped` entries rather than `continue`ing them into the void (#397's silent-drop class). The answer-block parser lives in the import-safe `views/components/wiki-integrate.ts` (the `synthesisTopicKey` precedent — server + PR 2's client share ONE implementation; tolerant of an optional VS16 on all four emoji, of `—`/`–`/`-`/`:`, and of a lowercase `claim`; the `###` anchor is deliberately NOT loosened). The one-shot runs through `src/wiki/integrate-oneshot.ts` — its own `factcheck-integrate` trace root + `factcheck` `/agents` run, `tracedOneShot` for the child span, 8k thinking cap, 90s timeout, and the bot config CLONED with `FENCED_EXCLUDED_TOOLS` unioned on (muninn #397: under `bypassPermissions` `allowedTools: []` fences NOTHING — an unfenced model would just `Edit` the page and bypass the preview + CAS + queue; the fence does NOT bind on `openai-compat`, which ignores `excludedTools`). ## View System

All pages are server-side rendered HTML via template literals. No build step, no framework.

### Component Pattern

Each component in `views/components/` exports up to three functions:

- `*Styles()` — returns a CSS string (injected into `<style>`)
- `*Html()` — returns an HTML string (injected into `<body>`)
- `*Script()` — returns a JavaScript string (injected into `<script>`)

Pages (`views/*.ts`) compose components by calling all three and concatenating into a full HTML document.

### Shared Infrastructure

- `views/shared-styles.ts` — CSS variables (colors, spacing), base reset, header, nav. Imported by all pages.
- `views/components/helpers.ts` — Inline JS utilities: `esc()` (HTML escaping), `extractToolInputLabel()`, formatting helpers.
- `views/components/agent-presence.ts` — the **agent presence chip** (mounted on `/wiki/gardener`, `/summaries`, `/wiki`). A tiny, embeddable "is a matching agent live (or about to be)?" indicator: standalone 15s poll of `GET /api/agents/overview` (NO second SSE — the host pages own their own loops), filtered by `{ kinds?, bot? }`, deep-linking to `/agents`. Three states — `running` (pulsing `.pulse-dot` + "<Kind>: <phase> <done>/<total>" label + optional "~Nm left" ETA from the overview `estimates` map), `preflight` (amber "<Kind> starts in Nm" from a matching `upNext` within `PRESENCE_HORIZON_MS` = 60 min), and `none` (renders NOTHING). ## Real-Time Updates

### SSE Endpoints (sse-routes.ts)

- `/api/events` — activity feed events (message_in, message_out, memory, error, etc.), plus `agent_status` (phase), `request_progress` (single-pane waterfall), and `agent_runs` (full AgentRun snapshot for `/agents`, throttled ~1/s)

### Agent Status (`src/observability/agent-status.ts`)

Tracks in-flight requests in a `Map<requestId, RequestProgress>` (concurrent requests no longer clobber a shared slot). The read side still surfaces a single primary request, so the SSE `/request-progress` contract and the waterfall UI are unchanged. See `src/observability/CLAUDE.md` for the full method list and the request-scoped-mutator rule.

1. `startRequest()` — creates RequestProgress keyed by a fresh requestId
2. `toolStart(requestId, …)`/`toolEnd(requestId, …)` — records tool calls with timing
3. `completeRequest(requestId, …)` — marks done, auto-clears that request after 30s
4. Phases: `idle`, `receiving`, `transcribing`, `building_prompt`, `calling_claude`, `saving_response`, `sending_telegram`, `sending_slack`, `synthesizing_voice`, `running_task`, `checking_goals`, `running_watcher`

### Activity Log (`src/observability/activity-log.ts`)

- In-memory ring buffer (max 500 events) + fire-and-forget DB persistence
- `loadFromDb()` called after DB init to hydrate on startup
- `stats` getter: messages today, avg response time, total cost

## MCP Debug Client (`src/ai/mcp-tool-caller.ts`)

- Supports both stdio (spawn process) and HTTP (StreamableHTTP) transports
- Connection pool keyed by `bot:server` — reuses existing connections
- Timeouts: 30s connect, 120s tool call
- Used by the MCP debug page (`tools-routes.ts`), Serena management, and the `openai-compat` connector

## Common Pitfalls

1. **SSE format**: Events must be `data: JSON\n\n` — missing double newline breaks the stream.
2. **Agent status waterfall is single-pane**: the data layer tracks all concurrent requests (per-`requestId` Map), but `/request-progress` emits only the primary (most-recently-started) request, so the overlay shows one at a time.
3. **Component pattern**: Always export all three (*Styles, *Html, *Script) even if empty — pages expect them.
4. **MCP connection cleanup**: Always call `disconnectServer()` or `disconnectAll()` — leaked stdio processes stay alive.
