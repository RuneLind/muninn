# Muninn CI

<!-- moved out of the root CLAUDE.md by /doctor on 2026-10-13 -->

`.github/workflows/ci.yml` runs these jobs on every push to `main` and every PR: `typecheck`, `audit`, `test-shard` (a three-way matrix that apt-installs ffmpeg so the real-ffmpeg tests run, then `bun run db:setup:test` and `bun scripts/test-chain.ts run --shard i/3`, below), `test` (the unit fan-in, below), `e2e-shard` (a four-way matrix: `db:setup:test` → `db:seed:e2e` → `bunx playwright test --test-list` on that shard's slice of the spec files), `e2e` (the fan-in, below) — both shard matrices against a `pgvector/pgvector:pg17` service published on **5435**, the port `src/test/test-db-url.ts` hardcodes — and `docker-build`, which needs no database: it builds the image twice (default, then `WITH_MEDIA=false WITH_CLI=false WITH_EMBEDDINGS=true`) and asserts what each one carries — including that only the second has the embedding-model cache, that a bogus build-arg value fails the build, that the bots/ COPY tolerates a context with no bot folder, and — by `docker inspect`, never by re-typing the expression — that the image pins `DASHBOARD_PORT`/`DASHBOARD_HOST` and declares the `/api/live` HEALTHCHECK. It carries a `timeout-minutes` because the claude.ai installer and the Debian mirrors are on its critical path.

**The unit shards and the fan-in.** package.json's `test` is generated by `bun scripts/test-chain.ts write` from the test files, the `mock.module` scan (each such file its own link), the own-process scan (`ownProcessFiles` in `src/test/mock-isolation.ts`: happy-dom `GlobalWindow` importers and `src/dashboard/views/wiki-boot/`, each its own link the same way), `PINNED` (whole links kept for other reasons, each with its reason), `EXCLUDED` and the groups in `scripts/unit-shards.json`; `scripts/test-chain.test.ts` fails when the committed chain differs from the generated one, or when a link is on no shard or two. A group keeps its directory arguments, so a new file under one joins it with no edit; a file anywhere else is a `write` error until it goes into a group. `write` also places each new link on the least-loaded shard. Each `test-shard` runner runs the `test` links the table puts on its shard, so `bun run test` locally runs CI's exact file sets one after another. Each link writes its own junit file, passed by the script, never in package.json. The `test` fan-in (`check`) fails when a shard's result is not `success`, a file the chain runs did not run exactly once, a `mock.module` or own-process file shared its process, or a link wrote no junit file, which it names as a crash; it warns when files missing from `scripts/unit-timings.json` took over 60 s. `check --shard i/3` checks one shard's junit locally. On a PR, shard 1 then times each test file the PR adds or changes, alone, and fails one over 10 s that `scripts/unit-slow-allowlist.txt` does not list; a file within 2 s of the bar is timed again. Timings: junit cannot give per-file time (bun writes `time="0"` on the file suite), so `refresh` times each file alone, wall clock, in the `unit-timings` job (`workflow_dispatch`), which uploads the table as an artifact; commit it, then `rebalance` regroups the group arguments onto the shards by it, in a PR of its own, because bun's file order depends on the set of files in a process.

**The e2e shards and the fan-in.** `scripts/e2e-shards.ts plan` packs whole spec files onto the four shards by the seconds in `e2e/shard-timings.json`, longest first; Playwright's own `--shard=i/n` balances by test COUNT and gave one shard half the suite's time. A stale table costs balance, never coverage; `bun scripts/e2e-shards.ts refresh e2e-results.json` rewrites it from the `e2e-report` artifact. Two places read the table. `plan` charges any spec missing from it the median, always, and shard 1 prints a `::warning::` per such spec. The fan-in's `check` fails when the specs in the merged report that are missing from the table took more than 60 s together (`UNTIMED_SECONDS_LIMIT`), naming each with its seconds. That sum covers every untimed spec in the run, so seconds already untimed on main count toward a PR's total. Clear it by refreshing from the e2e-report artifact of a run of the same branch whose shards all passed (the guard's own run, if the guard is its only failure), so the untimed specs are in the report. A timed spec that slows down never trips it. The `e2e` job merges the shards' blob reports and runs `scripts/e2e-shards.ts check` against `playwright test --list`: every listed test ran exactly once, and the skipped set, each skip with its reason, equals `e2e/ci-expected-skips.txt` — a new skip, a listed one that ran, or a listed one that skipped for a different reason is red. Tests skipped after a failure in the same file (a serial describe, a throwing `beforeAll`) are left to the shard's red rather than blamed as skips. A skip that is deliberate on a runner gets a line there; a skip that is not is the missing-fixture failure the list exists to catch.

`audit` is `bun audit --audit-level=high`. It exists because the lockfile is a result and not a promise: the image this repo's nais deployment ran until 2026-09-14 carried 42 npm Critical/High findings across 14 packages, nearly all of them under `@slack/bolt`, `@modelcontextprotocol/sdk` and `@huggingface/transformers` rather than in anything this repo names, and `bun install --frozen-lockfile` in the Dockerfile faithfully rebuilt them on every deploy. This job is red on **41 of those 42**. A hand-written list of minimum versions was tried first and rejected in review: it cannot see an advisory published after it was written, and the one built from Docker Scout's data had already set axios a floor too low to catch GHSA-gcfj-64vw-6mp9.

Three things about it that a green result does not mean, all measured rather than assumed. **It reads the lockfile, so it sees only what the lockfile places** — the 42nd finding was an `adm-zip` vendored inside `@github/copilot`'s platform binary, which no lockfile names and no lockfile audit can reach; OS packages and native libraries are equally invisible. Scanning the *image* belongs to the pipeline that builds it. **Its output prints one advisory's range, not the union** — on `origin/main` it says `axios >=1.0.0 <1.15.2` while the real floor is 1.18.0, so reading a fix off the red line reproduces exactly the mistake the deleted floor list was made of. And **`--ignore` takes GHSA ids only**, whatever `bun audit --help` says about CVE ids: on bun 1.3.10 a CVE id is silently discarded and the job stays red. A red here is a finding to fix or to suppress by GHSA id, never a flake to re-run — and unlike the other jobs, a red is a fact about this repo's dependencies rather than about a floating base tag or a browser download.

A runner has **no `.env` at all**, which is the point: it is the only place the suites are pinned to what the repo says rather than to whichever machine last ran them. Two things follow from that and are deliberate:
- **`workers: 1` on CI, `retries: 0` everywhere.** Most spec files boot a muninn of their own, several boot two or three (`MUNINN_LOCAL_ROLE` is per-process, so admin and `user` cannot share one), and some restart theirs mid-file; every other server a spec starts — for example a stub huginn, Texas, claude-usage ledger, GCS bucket, model API, Vimeo oEmbed or plain origin page — is an in-process `node:http` stub, not a process, so `src/index.ts` is the only server a spec spawns. List the stub-starting spec files with `grep -l createServer e2e/*.spec.ts`. Count the booting spec files with `grep -l '"src/index.ts"' e2e/*.spec.ts | wc -l` instead of trusting a number written here: every new spec moves it. They run beside the config's own shared server on 3011; on a 4-core runner the contention shows up as a click landing before the page's inline script attached its listener — a different spec each run. Serial removes it; a retry would have turned it into a silent pass. CI's parallelism comes from the four shard runners instead, each as loaded as one serial run.
- **Only `bots/jarvis/` is tracked**, so CI has one bot, and the bot-switch cases in `inspector` and `wiki-chat-dialog` skip themselves and say so. Six `jira-card` cases skip too — they are opt-in behind `JIRA_CARD_THREAD`/`_USER`/`_DRAFT` — and `wiki-agent-lens` skips its real plan-card case, since a runner has no claude-skills checkout. `e2e/ci-expected-skips.txt` is the authority for this list.

## Test-chain tooling and the mock.module leak

`bun run test:count` reports how many tests the repo has, grouped unit / integration / e2e. It groups by the `test*` chains rather than by directory, since a chain is where the repo decides what a test needs to run: `db/postgres-connection.test.ts` runs in `test:unit` and `db/provision.test.ts` beside it in `test:db`. A chain that needs Postgres or a live server is integration, so `test:hivemind` counts as integration. By default it counts declarations, which reads low, because a test declared in a loop or a `.each` table counts once. `-- --run` measures instead: it runs the bun chains once each, takes back out any file two chains of one group both run (unless a chain that runs it failed), and lists the e2e specs with `playwright test --list` without running them. It skips `test:integration`, which needs `bun run dev` on 3010 and makes real Claude calls, and exits non-zero when a chain fails. `-- --files` gives the per-file list and `-- --json` a machine-readable version. It also reports where the chains have drifted apart: test files no chain runs, files only `test` runs, and grouped files `test` skips, so CI never runs them.

**And the leak is order-dependent in a way no developer machine shows:** `bun test` runs files in an order of its own — not argv order, not alphabetical — that depends on the SET of files in the run: on the same GitHub runner, main run #508 loaded `src/chat/chat-config.test.ts` before `src/ai/haiku-direct.test.ts` (green) and #509, which added one test file and touched no chain, loaded them the other way round (red: `getDb().unsafe is not a function` from the `db/client.ts` mock — 19 red `test` jobs 2026-09-03 → 09-05 with that one green between them), while the mini ordered the same set as #508 every time. So a mock in a shared process is green or red per (machine, file set) and flips on any commit that adds a test file; "passes locally" and "CI was green last week" are both non-evidence. Once that file was isolated, `src/watchers/anthropic.test.ts`'s partial `db/summary-candidates.ts` mock inside the one-argument `bun test src/watchers/` link reached `runner.test.ts` → `x.ts` on the runner's order (`Export named 'upsertDestinationCandidate' not found`) — and failed to link its OWN import graph the moment it ran alone, masked until then by `x.test.ts`'s fuller mock loading first.
