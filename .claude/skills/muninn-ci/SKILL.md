# Muninn CI

<!-- moved out of the root CLAUDE.md by /doctor on 2026-10-13 -->

`.github/workflows/ci.yml` runs six jobs on every push to `main` and every PR: `typecheck`, `audit`, `test` (apt-installs ffmpeg so the real-ffmpeg tests run, then `bun run db:setup:test` and the full `bun run test` chain), `e2e-shard` (a four-way matrix: `db:setup:test` → `db:seed:e2e` → `bunx playwright test --test-list` on that shard's slice of the spec files), `e2e` (the fan-in, below) — `test` and the shards against a `pgvector/pgvector:pg17` service published on **5435**, the port `src/test/test-db-url.ts` hardcodes — and `docker-build`, which needs no database: it builds the image twice (default, then `WITH_MEDIA=false WITH_CLI=false WITH_EMBEDDINGS=true`) and asserts what each one carries — including that only the second has the embedding-model cache, that a bogus build-arg value fails the build, that the bots/ COPY tolerates a context with no bot folder, and — by `docker inspect`, never by re-typing the expression — that the image pins `DASHBOARD_PORT`/`DASHBOARD_HOST` and declares the `/api/live` HEALTHCHECK. It carries a `timeout-minutes` because the claude.ai installer and the Debian mirrors are on its critical path.

**The e2e shards and the fan-in.** `scripts/e2e-shards.ts plan` packs whole spec files onto the four shards by the seconds in `e2e/shard-timings.json`, longest first; Playwright's own `--shard=i/n` balances by test COUNT and gave one shard half the suite's time. A spec the table does not know costs the median, so a stale table costs balance, never coverage, and shard 1's `plan` prints a `::warning::` naming each such spec; `bun scripts/e2e-shards.ts refresh e2e-results.json` rewrites it from the `e2e-report` artifact. The `e2e` job merges the shards' blob reports and runs `scripts/e2e-shards.ts check` against `playwright test --list`: every listed test ran exactly once, and the skipped set, each skip with its reason, equals `e2e/ci-expected-skips.txt` — a new skip, a listed one that ran, or a listed one that skipped for a different reason is red. Tests skipped after a failure in the same file (a serial describe, a throwing `beforeAll`) are left to the shard's red rather than blamed as skips. A skip that is deliberate on a runner gets a line there; a skip that is not is the missing-fixture failure the list exists to catch.

`audit` is `bun audit --audit-level=high`. It exists because the lockfile is a result and not a promise: the image this repo's nais deployment ran until 2026-09-14 carried 42 npm Critical/High findings across 14 packages, nearly all of them under `@slack/bolt`, `@modelcontextprotocol/sdk` and `@huggingface/transformers` rather than in anything this repo names, and `bun install --frozen-lockfile` in the Dockerfile faithfully rebuilt them on every deploy. This job is red on **41 of those 42**. A hand-written list of minimum versions was tried first and rejected in review: it cannot see an advisory published after it was written, and the one built from Docker Scout's data had already set axios a floor too low to catch GHSA-gcfj-64vw-6mp9.

Three things about it that a green result does not mean, all measured rather than assumed. **It reads the lockfile, so it sees only what the lockfile places** — the 42nd finding was an `adm-zip` vendored inside `@github/copilot`'s platform binary, which no lockfile names and no lockfile audit can reach; OS packages and native libraries are equally invisible. Scanning the *image* belongs to the pipeline that builds it. **Its output prints one advisory's range, not the union** — on `origin/main` it says `axios >=1.0.0 <1.15.2` while the real floor is 1.18.0, so reading a fix off the red line reproduces exactly the mistake the deleted floor list was made of. And **`--ignore` takes GHSA ids only**, whatever `bun audit --help` says about CVE ids: on bun 1.3.10 a CVE id is silently discarded and the job stays red. A red here is a finding to fix or to suppress by GHSA id, never a flake to re-run — and unlike the other jobs, a red is a fact about this repo's dependencies rather than about a floating base tag or a browser download.

A runner has **no `.env` at all**, which is the point: it is the only place the suites are pinned to what the repo says rather than to whichever machine last ran them. Two things follow from that and are deliberate:
- **`workers: 1` on CI, `retries: 0` everywhere.** Most spec files boot a muninn of their own, several boot two or three (`MUNINN_LOCAL_ROLE` is per-process, so admin and `user` cannot share one), and some restart theirs mid-file; every other server a spec starts — a stub huginn, Texas, claude-usage ledger, GCS bucket or plain origin page — is an in-process `node:http` stub, not a process, so `src/index.ts` is the only server a spec spawns. List the stub-starting spec files with `grep -l createServer e2e/*.spec.ts`. Count the booting spec files with `grep -l '"src/index.ts"' e2e/*.spec.ts | wc -l` instead of trusting a number written here: every new spec moves it. They run beside the config's own shared server on 3011; on a 4-core runner the contention shows up as a click landing before the page's inline script attached its listener — a different spec each run. Serial removes it; a retry would have turned it into a silent pass. CI's parallelism comes from the four shard runners instead, each as loaded as one serial run.
- **Only `bots/jarvis/` is tracked**, so CI has one bot, and the bot-switch cases in `inspector` and `wiki-chat-dialog` skip themselves and say so. Six `jira-card` cases skip too — they are opt-in behind `JIRA_CARD_THREAD`/`_USER`/`_DRAFT` — and `wiki-agent-lens` skips its real plan-card case, since a runner has no claude-skills checkout. `e2e/ci-expected-skips.txt` is the authority for this list.
