| `DATABASE_URL` | Yes | — | Postgres connection string. The two `db/` CLI scripts (`migrate.ts`, `require-provisioned.ts`) also read **`DB_URL`** as a fallback (`db/database-url.ts`, DATABASE_URL wins) — nais injects credentials under the manifest's `envVarPrefix: DB`, and the pod remedies (`kubectl debug`, a naisjob `command:`) bypass the entrypoint that maps one to the other. The server itself reads only `DATABASE_URL`. **Whichever variable it comes from, the URL is translated before `postgres()` sees it** (`db/postgres-connection.ts` → `openPostgres`, the only sanctioned way to construct a client — pinned by a test that walks `src/` and `db/`): a nais Cloud SQL instance is private-IP with client certificates, so `DB_URL` carries `?sslcert=…&sslkey=…&sslrootcert=…&sslmode=verify-ca`, and postgres.js reads NONE of it as TLS material — it forwards unknown query parameters into the **startup packet**, so the connection dies with `unrecognized configuration parameter "sslcert"` (measured). The translation strips the whole `ssl*` family (keeping `sslnegotiation`, which postgres.js does read), repairs the `??` nais has been seen to inject, reads the files and hands over the `ssl` OBJECT. `verify-ca` waives the hostname check — a Cloud SQL certificate names the instance while the URL dials an IP — and `verify-full` against a bare IP is **refused, not downgraded**: the driver sets no `servername` for an IP host and the runtime then runs no identity check and calls no `checkServerIdentity` callback either, so honouring it is impossible (measured twice; the first repair was inert). A plain URL is passed through untouched. End-to-end proof against a real TLS server with a client certificate: `bun scripts/smoke-nais-db-tls.ts`. |

| `MUNINN_PROFILE` | No | *(unset ⇒ `default`)* | **Which deployment this process is** — the serving-profile switch, parsed fail-CLOSED like `MUNINN_AUTH` and unlike `optionalEnvFlag`: unset (or blank) is today's muninn, `nais` is the pod, and **any other value throws at load**, because the degrade direction here is "serve the full surface". `nais` does five things, all of them removals but one admitted write (below). (1) `createDashboardRoutes` does not REGISTER fourteen route groups — wiki (everything on the wiki surface except the read slice), wiki-gardener, plans, sync, claude-usage, benchmark, logs, summaries and the six capture verticals (anthropic, article, youtube, x-article, tiktok, vimeo) — so they answer **404 with no handler**, not 403: the first six are bound to working trees and a launchd service that do not exist in a pod, `/api/logs*` serves the JSONL sink and its message previews, and the verticals need binaries the nais image is built without (`yt-dlp`/`ffmpeg`/the Claude CLI, and for Vimeo a Chromium that is an operator step even on a laptop). `summaries` is there under the same rule read the other way — **a dropped group takes its HTML surface with it**: that page's every control POSTs to `/api/anthropic/*`, `/api/articles/summarize` or `/api/wiki/share`, so keeping it would render a page that 404s into a generic error on the first click. The five inline instance routes (`/`, the two health paths, the favicons, the build hash, `/api/attention`) and the separately-mounted `/chat` slice are always present. So is the **wiki read slice** (`wiki-read`: `/wiki`, `/api/wiki/{pages,page,page/provenance,related,decision-chain,html,graph}`) — the reader over a read-only mirror, serving read-only roots only (`routes/wiki-read-scope.ts`), whose eight GET paths join the auth user zone under this profile only (`WIKI_READ_SLICE_PATHS` in `src/auth/zones.ts`, exact paths, GET/HEAD, admitted by `servesWikiReadSliceOnly`; on `default` role `user` gets 403 there), and beside them the one write the profile admits: GET/HEAD/POST `/api/wiki/answers` for role `user` (`WIKI_READ_SLICE_METHOD_ENTRIES`); the page stamps `body.wiki-read-slice` and hides every control that would reach the dropped `wiki` group (`views/components/wiki-read-slice.ts`, pinned by `e2e/wiki-nais-read.spec.ts`). (2) `renderNav` omits the links to those groups, on every page including `/chat` and `/wiki` — role `user` gets no nav at all, starts with the whole header hidden (`m` shows it) and lands on `/wiki` from `/` — via the same drop set (`src/dashboard/route-groups.ts`, which owns `ROUTE_GROUPS`, `NAIS_DROPPED_ROUTE_GROUPS` and `droppedRouteGroups`; it is its own module because a view importing the route factory would be a cycle). (3) The inbound-message preview line in `src/core/message-processor.ts` drops from `info` to `debug` — a pod's stdout is a shared aggregator; the `activity_log` row keeps the full text (admin zone by design). NB the Slack handlers, `voice-handler.ts` and `response-handler.ts` log previews of their own and are NOT covered (follow-up). (4) The Claude-CLI refusal is in **`spawnHaiku` itself** (`src/ai/haiku-cli-unavailable.ts`), which is the ONE door — so it covers the Haiku router's fallback, a bot that asks for the `cli` backend, AND the direct callers the router never sees (`src/watchers/{email,x,anthropic}.ts`); the router's job is only to hand down WHICH backend it tried and why, so the thrown `HaikuCliUnavailableError` names the missing credential rather than the missing binary. (5) It pairs with the image built `--build-arg WITH_MEDIA=false --build-arg WITH_CLI=false --build-arg WITH_EMBEDDINGS=true`; the first two default ON and the third OFF, so docker-compose's build is unchanged. `WITH_EMBEDDINGS` bakes `Xenova/all-MiniLM-L6-v2` (~23 MB) into `node_modules/@huggingface/transformers/.cache/` at build time **through the throwing path** — `warmupEmbeddings()` catches and logs, so a builder with no egress would succeed and ship an empty cache, which is the exact silent degradation the bake removes (nais egress is default-deny, and a pod whose memory search returns nothing still reports healthy). CI asserts both directions. The parse is one function, `resolveServingProfile()` in `src/config.ts` (renamed away from `resolveProfile`, which `src/research/corpus.ts` already exports for the research corpus). **The pair rule: a `Config` field where a `Config` exists (`config.profile ?? resolveServingProfile()` in the route factory), the env getter where none does (`renderNav`, the CLI guard) — one parse either way.** The variable is in `AMBIENT_INSTANCE_ENV` so no suite inherits it from a developer's `.env`, and a `nais` boot logs one line naming the dropped surface. |

| `CLAUDE_USAGE_URL` | No | `http://127.0.0.1:8787` (applied at the route, not on `Config`) | Base URL of the **claude-usage** pipeline-ledger service (launchd, port 8787 on the mini), read **server-side** by `GET /api/claude-usage/overview` for the `/models` **Pipeline ledger** card. Muninn reads only `GET /api/pipeline?days=N` (clamped 1–90, default 14) over HTTP, bounded in time (**10 s**) AND in bytes (**8 MB**, content-length plus a bounded read for chunked bodies) — never claude-usage's sqlite file (schema drift + a 145 MB synchronous `bun:sqlite` read on the event loop, which is also what the byte cap is sized against); the 90-day worst case measures **640 KB / ~0.2 s** (2026-08-13), so the 10 s budget is deliberate slack, not a tight fit. `config.claudeUsageUrl` is **null when unset** — one trimmed read, so a whitespace-only value cannot report "configured" while pointing nowhere — and `configured` is derived from that null at the route (the `src/sync/` idiom). The browser never reaches the service (tailnet viewers + mixed content under `tailscale serve`), so the card renders no external link and instead NAMES the effective base URL in its sub-line and in every degrade message. Unreachable/non-200/oversized/timeout ⇒ 200 + `errors[]` + an honest "claude-usage unreachable" note, never a 5xx (and a persistently-down service warns once per distinct error, then drops to info — the card is polled every 5 min by every open tab); setting this var explicitly is also what keeps the card VISIBLE on a host where the service is down — left unset and unreachable, the card hides. **The `/wiki` listing reads this host too**, server-side and through the same bounds: `GET /api/files?root=<wiki root>&summary=1` fills the reader's WORKED-ON date axis (`src/wiki/worked-ledger.ts`), background-refreshed per wiki root and never awaited, with an unset value meaning the axis is simply off. **The find palette's Everywhere section (`GET /api/wiki/find-everywhere`) sends this host the reader's typed free text** — filter tokens dropped, capped at 200 code points and 12 words — through `claudeUsageJson`, bounded at 3 s and 2 MB; unset ⇒ that leg reports `unconfigured`. |
